# OPERATIONAL_REASONING_NOTES.md

## Which Sections Are Deterministic

Every section in the report is deterministic. This is worth stating plainly because it's a departure from what "AI-generated narrative text" (this task's own Section 1 wording for the Executive Summary) might imply.

- Site Activity Snapshot: direct counts from real database queries (events, resolved items, blockers, approvals, photos). No interpretation.
- Work Completed Today: the literal text_input field from today's events and the literal title/name of resolved items. No summarization, no rewriting.
- Blockers & Risks: the literal blocker's own title, a computed age (a simple timestamp subtraction), and an impact category derived from a fixed, explicit lookup table (_CATEGORY_TO_IMPACT) mapping each existing operational item category to one of five impact categories. Every mapping is a direct, auditable dictionary entry - there is no inference step a reader can't see by reading the table itself.
- Client Decisions Pending: the same literal-field pattern as Blockers.
- Commercial Attention: the literal kind of each commercial event that occurred today, filtered to a fixed allowlist of three kinds. No amounts are narrated in prose - the underlying Commercial Engine's own numbers remain in the existing Commercial Workspace, unrepeated here, avoiding any risk of the report's own text drifting out of sync with the authoritative figures.

## Which Sections Use "AI Summarization" — and What That Actually Means Here

Executive Summary and AI Forecast Impact are the two sections this task's own brief describes as narrative. Both are built by _build_executive_summary() and _build_forecast_impact() - deterministic Python functions that compose sentences from an if/elif chain conditioned directly on the same real computed values every other section uses (blocker count, health status, pending-approval count). No LLM call is made anywhere in this service.

This was a deliberate choice, not a shortcut, and it's worth explaining why. This task's own Section 1 says the Executive Summary "should be AI-generated narrative text, not a static template" - but it also explicitly warns, twice, against fabricating operational facts or precise forecasts. A real LLM call summarizing today's activity carries genuine hallucination risk: it could invent a fact not present in the underlying data, misstate a count, or produce a forecast day-count that sounds specific and confident but isn't actually computed from anything. Template composition over verified data cannot do any of these things - every clause in the output traces to a specific, named computed value, the same standard CRE's own evaluate_rules already holds itself to for insight generation. "Narrative," in this report, means readable prose assembled from trusted numbers - not free-form text generation. This is the stronger, more defensible interpretation of "AI-generated," and the one consistent with Atlas's own explainable-intelligence principle this document is asked to protect.

If a future pass wants genuine LLM-generated prose for these two sections, the safest path is composing the same deterministic values into a prompt and constraining the model's own output format tightly (e.g., "rewrite the following sentences for readability without adding or removing any fact") - never asking a model to look at raw events and infer a summary on its own.

## Confidence Assumptions

The AI Forecast Impact section always returns one of three qualitative confidence levels, and the rule for choosing one is simple and stated in code, not hidden in a model's own reasoning:

- High confidence: no open blockers at all - a genuinely confident, verifiable statement ("nothing is currently blocking this project").
- Moderate confidence: open blockers exist and are schedule-impacting, and the project's own overall health signal is not green (amber/red) - the blocker's existence is corroborated by an independent signal (Explain Health), giving a more confident basis for expecting real schedule impact.
- Low confidence: open blockers exist but overall health is still green - the report surfaces the blocker honestly, but flags lower confidence that it will actually manifest as schedule impact, since the independent health signal doesn't yet corroborate it.

No numeric confidence score is ever produced (e.g., "73% confidence") - this task's own brief explicitly asks for qualitative levels only, and a fabricated-looking numeric score would misrepresent the actual precision of what's being computed.

## How Hallucinated Operational Facts Are Prevented

Three concrete mechanisms, not just an intention:

1. No LLM is called for any section of this report. The most direct prevention available - a fact that was never generated by a language model cannot be a language-model hallucination.
2. Every narrative sentence traces to one specific computed value. A reviewer can read _build_executive_summary() or _build_forecast_impact() top to bottom and match every clause in the output to the exact variable that produced it - there is no step where "the model decided" something not visible in the code.
3. Absence is reported as absence, never invented. When Atlas has no data for a section (Manpower/Materials tracking don't exist in Atlas today, confirmed absent - the same finding PX-02's own Workspace Architecture document already made), that section is either omitted or shown with an honest "no activity" statement - never filled with plausible-sounding placeholder content. The Attached Photo Summary's own thumbnail note ("not yet supported by the current UI") is the same discipline applied to a UI capability gap, not a report-data gap.
